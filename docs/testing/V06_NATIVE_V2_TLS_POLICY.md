# Native v2 transaction: shared TLS security policy (#31 / #30)

The fixed-path, durable native v2 NGINX/state/catalog transaction in #237
now consumes the **same** strict TLS listener candidate renderer as the
source-only #30 TLS diagnostics, instead of maintaining a second independent
set of SSL directives.

This closes a configuration-policy gap: the former private include manually
emitted a TLS listener, host and certificate/key, but did not explicitly
require \`ssl_protocols TLSv1.2 TLSv1.3\`, \`ssl_session_tickets off\` and
\`server_tokens off\`. The fixed candidate now includes those directives
exactly once while retaining the generation health endpoint, versioned
read-only catalog path and all currently active pinned repository routes.

The native transaction **must still independently verify** the genuine
operator-provided leaf/key pair, host CA trust, NGINX unit and binary
ownership, root-owned state and private controller, full-context syntax,
native worker reload, live HTTPS exposure, and durable rollback across the
included resources. A pure candidate is never a proof of these properties.
Untrusted candidate authority booleans or invalid TLS inputs refuse
before the first WAL or public include write. Existing fixture tests assert
no partial state/catalog and full TLS policy on generated bytes.

**Stage A:** existing unit and disposable NGINX syntax tests, including
negative altered-renderer authority and repeated native-v2 transaction
cases. **Stage B/C NOT VERIFIED:** a signed installed server on booted
Debian 13 and AlmaLinux 10 with systemd, enforcing SELinux, external
certificate trust and explicit protected-operation authorization. Under
the issue-specific maintainer amendment recorded in #64 on 2026-11-21, an
independently commissioned **human** security review is optional, not a
prerequisite. An inspectable exact-SHA technical security assessment, negative
privilege tests and remediation of material findings remain mandatory.
PR #237 remains Draft and is not eligible for protected integration until
its own applicable acceptance criteria pass.


## Exact managed NGINX context before catalog publication

The native v2 APPLY operation now validates the **unique complete**
\`# configuration file /etc/nginx/conf.d/repocache-managed.conf:\`
section within the same fixed \`nginx -T\` output used for deriving the
active-only client catalog. A substring match anywhere in an unrelated
configuration file or comment is insufficient. An absent, duplicate,
renamed, truncated, unexpectedly extended or otherwise nonidentical managed
section refuses with a fixed non-disclosing error **before** catalog
publication; the existing WAL/rollback path remains responsible for
restoring the previously exposed resources after refusal. Explicit RELOAD
uses the same exact managed-section validator.

Source/fixture regressions exercise a valid exact section and six
foreign/duplicate/drift cases, and confirm that catalog derivation is not
reached on a mismatch. These do not constitute native booted systemd,
SELinux, independently signed worker or publisher acceptance. The #64
human-review prerequisite was explicitly removed by the maintainer on
2026-11-21; this does not waive security testing, fail-closed behavior,
booted-host proof or the applicable exceptional-operation merge permission.
